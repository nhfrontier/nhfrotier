# FR-15 UX 리스크 검토 v1.0

> **관련 문서**: [기능명세 인덱스](개발문서/기능명세/00_INDEX.md) | [PRD](개발문서/01_PRD.md) | [IA·화면](개발문서/03_IA_FUNCTION_SPEC.md) | [API/DB](개발문서/05_API_DB_SPEC.md) | **렌즈 정본**: [USABILITY_REVIEW.md](docs/guidelines/USABILITY_REVIEW.md)

## 1. 개요

담당자가 요청하면 AI가 **화면 전체와 그 화면을 두고 오간 의견 전체를 함께 읽고**, 담당자들이 짚지 못한 사용성 문제를 의견 패널에 카드로 올리는 기능이다. 담당자는 각 지적에 대해 반영 / 보류 / 반려를 결정한다.

여섯 개 렌즈로 본다 — **누적과 반복 / 흐름 중단 / 예외 상황 / 되돌리기·오조작 / 사용 맥락 / 빠진 이해관계자**. 렌즈 정본은 [docs/guidelines/USABILITY_REVIEW.md](docs/guidelines/USABILITY_REVIEW.md)이며, 이 문서는 그 렌즈를 제품 기능으로 어떻게 운용하는지를 정의한다.

**왜 필요한가**: 의견 패널에는 기획·개발·디자인 담당자가 각자의 관점으로 코멘트를 남긴다. 그런데 **각 의견이 개별로는 타당한데 합쳐 놓으면 사용자가 불편해지는 경우**를 아무도 짚지 못한다. "가입 완료 안내 팝업", "약관 변경 팝업", "혜택 안내 모달", "앱 평가 요청"이 각기 다른 의견에서 나오면 하나하나는 다 필요해 보이지만, 사용자는 한 흐름에서 팝업을 네 번 닫아야 한다.

## 2. 비범위 — 이 기능이 하지 않는 것

**[PRD 5절](개발문서/01_PRD.md)의 "자동 승인 또는 준법 판단의 완전 자동화" 비범위를 그대로 승계한다.** FR-15는 그 경계를 넓히지 않으며, [08 Q2](개발문서/08_DECISIONS_OPEN_ISSUES.md)("AI는 제안하고 최종 반영은 담당자가 결정한다")를 따른다.

| 한다 | 하지 않는다 |
|---|---|
| "이 흐름에서 팝업을 네 번 닫아야 합니다" | "이 설계는 잘못되었습니다" — 품질 판정 |
| 화면·의견에서 **그대로 인용한 근거**를 제시 | 근거 없이 인상을 말한다 |
| 담당자에게 판단 재료 제공 | 담당자 대신 판단 |
| 사람이 놓친 관점을 하나 더 얹는다 | 사람의 의견을 대체하거나 반박 |
| 의견으로 노출 | 생성·Export·공유 **차단** |
| 담당자가 요청할 때 실행 | 논의에 상시 끼어들기 |

**특히**: 이 검토는 다른 팀원의 의견을 읽고 나온 것이다. 그러므로 **특정 의견이나 작성자를 지목해 틀렸다고 말하지 않는다.** "이 결정들이 합쳐지면 이런 결과가 됩니다"까지만 말한다.

## 3. FR-14와의 경계

파이프라인 구조는 [FR-14 책임성 검토](개발문서/기능명세/FR-14_책임성검토.md)와 같지만 다섯 가지가 다르다. **한 기능으로 합치지 않는 이유**가 이 표다.

| | FR-14 책임성 검토 | FR-15 UX 리스크 검토 |
|---|---|---|
| 입력 | 화면 HTML + 기획안 | **전 화면 HTML + 기획안 + 의견 전문** |
| 기준 | 규칙 21개 (`RR-xx`, "이러면 위반") | **렌즈 6개 (`UR-xx`, "이걸 물어봐라")** |
| 판정 단위 | 요소 하나로 성립 | **여러 결정이 쌓인 결과** |
| 실행 | 생성 직후 자동 + 수동 재실행 | **담당자 요청 시에만** |
| 결과 위치 | `AI 검토` 탭 (별도) | **`의견` 탭에 사람 댓글과 섞여서** |
| 결정 | 반영/보류/반려/**준법 검토 요청** | 반영/보류/반려 |

경계 규칙: **요소 하나로 답이 나오는 것은 FR-14의 몫이다.** 팝업 4개처럼 개수와 맥락이 문제인 것만 FR-15가 본다.

## 4. 동작 상세

### 4-1. 생성 가드레일을 두지 않는 이유

FR-14는 규칙에서 파생한 설계 기본값을 생성 프롬프트에 주입한다(FR-14 3-1). FR-15는 **그에 해당하는 가드레일을 두지 않는다.**

렌즈는 위반 조건이 아니라 질문이라 생성 시점에 주입할 제약이 못 된다. "누적을 조심하라"는 지시는 화면 한 장을 만드는 프롬프트에서 의미가 없고, 생성 프롬프트를 더 길게 만들면 FR-14 가드레일과 섞여 양쪽 다 약해진다. FR-15는 **사후 검토 하나만** 한다.

### 4-2. 실행 — 담당자 요청 시에만

- 자동 실행하지 않는다. 의견 패널의 `AI에게 검토 요청` 버튼으로만 돈다.
- **왜 수동인가**: 댓글마다 자동 실행하면 같은 지적이 반복되어 스레드를 오염시킨다. 논의가 어느 정도 쌓였을 때 사람이 부르는 편이 결과가 낫고, 비용·지연이 예측 가능하다.
- 재실행은 이전 검토를 덮어쓰지 않는다. 새 검토 이력을 만들고 이전 결정은 그대로 보존한다. (FR-14와 동일)
- 누가 요청했는지 기록한다(`requested_by`).

### 4-3. 입력

세 가지를 한 번에 넣는다. **나눠 부를 수 없다** — 누적을 보려면 흐름 전체가 한 컨텍스트에 있어야 한다.

| 출처 | 내용 |
|---|---|
| `PROPOSAL` | 기획안 본문 |
| `SCREEN` | **전 화면**의 HTML (첫 화면만이 아니다). **(2026-09-08) 저장본이 아니라 요소 편집을 반영한 HTML을 넣는다** — 저장본을 넣으면 사람이 이미 고친 것을 AI가 다시 지적한다 → [FR-09](개발문서/기능명세/FR-09_버전관리.md) baking |
| `DISCUSSION` | 의견 패널의 코멘트 전문. `[의견 #3] 작성자 · 화면 s02 / 요소 nh-14` 형태로 번호를 매겨 넘긴다 |

의견에 번호를 매기는 이유는 지적 카드에서 "의견 #3"으로 되짚을 수 있어야 하기 때문이다.

입력 총량에 상한을 둔다. 초과하면 **잘라내지 않고 거부한다** — 잘린 뒷부분에 있던 팝업을 못 보면 결과가 조용히 틀린다.

### 4-4. 근거 검증 — FR-14보다 엄격하다

렌즈는 규칙보다 느슨하다. 그래서 근거 검증을 한 단계 더 조인다.

| | FR-14 | FR-15 |
|---|---|---|
| 요구 | `evidence`가 비어 있지 않을 것 | `evidence_quotes` 1~3개 |
| 검증 | 비어 있으면 버린다 | **원문에 글자 그대로 존재하는지 대조**한다 |
| 탈락 조건 | 빈 근거 | 살아남은 인용이 0개 |

- 검증 코퍼스는 기획안 + 전 화면 HTML + 전 의견 본문이다. 공백을 정규화하고 소문자화한 뒤 부분문자열로 대조한다. 너무 짧은 조각은 우연히 맞을 수 있으므로 무시한다.
- **살아남은 인용이 하나도 없으면 그 지적을 통째로 버린다.** 요약·의역은 탈락한다.
- 렌즈 ID가 정본 목록에 없어도 버린다.
- 지적할 것이 없으면 빈 결과를 그대로 보고한다. **억지로 채우지 않는다** — 검증 불가능한 카드가 한 장이라도 섞이면 나머지 카드까지 읽히지 않는다.

### 4-5. 결정

담당자는 각 지적에 대해 셋 중 하나를 고른다. [FR-08](개발문서/기능명세/FR-08_반영결정.md) 및 FR-14와 같은 체계다.

| 결정 | 의미 |
|---|---|
| 반영 | 지적을 받아들여 고친다 |
| 보류 | 지금은 두고 나중에 판단한다 |
| 반려 | 지적이 타당하지 않다 |

`준법 검토 요청`은 두지 않는다 — 준법 축은 FR-14 고유다. UX 리스크에서 준법 사안이 보이면 그것은 RR 규칙의 대상이며 FR-14가 잡는다.

결정은 **누가·언제** 했는지와 함께 기록된다.

### 4-6. 의견 흐름에의 결합

- AI 지적은 사람 댓글과 **같은 목록에 시간순으로 섞여** 표시된다. 별도 탭으로 빼지 않는다 — 논의에 얹는 것이 이 기능의 요지이기 때문이다.
- **AI 카드와 사람 댓글은 시각적으로 구분한다** — AI 카드는 좌측 보더와 `AI` 표기, 사람 댓글은 아바타 ([03 UX 원칙](개발문서/03_IA_FUNCTION_SPEC.md)).
- 저장은 별도 테이블에 한다. 근거·심각도·결정 필드를 `comments`에 억지로 넣지 않으며, AI가 사람 작성자로 위장하지도 않는다.
- 캔버스 메모 핀 번호는 **사람 댓글만 세어** 매긴다. AI 카드가 번호를 밀면 화면 위의 핀과 목록이 어긋난다.

### 4-7. 운영 스택에서의 호출 경로

브라우저는 LLM을 직접 호출하지 않는다. 검토 호출은 AI Orchestrator 경유 서버 측 호출이며, 장시간 처리 시 비동기 Job 규칙을 따른다 → [FR-05](개발문서/기능명세/FR-05_AI제작.md) · [ARCHITECTURE 2·3절](docs/architecture/ARCHITECTURE.md)

## 9. 설계 판단 기록

- **왜 FR-14에 합치지 않는가**: 3절 표의 다섯 가지가 다르다. 특히 입력(전 화면+의견)과 실행 시점(수동)이 달라 한 함수에 넣으면 조건 분기가 늘고, 규칙과 렌즈가 한 프롬프트에 섞여 양쪽 결과가 다 흐려진다.
- **왜 규칙이 아니라 렌즈인가**: 팝업 4개는 요소를 아무리 들여다봐도 잡히지 않는다. 개수와 맥락이 문제이지 개별 요소는 멀쩡하다. 조건으로는 쓸 수 없어 질문으로 둔다.
- **왜 근거 대조를 FR-14보다 조이는가**: 렌즈가 느슨한 만큼 지어낸 근거가 통과할 여지가 커진다. 검증 불가능한 카드는 담당자가 판단할 수 없고, 한 장만 섞여도 나머지 카드까지 읽히지 않는다.
- **왜 별도 테이블인가**: 근거·심각도·결정 필드를 `comments`에 붙이면 사람 댓글의 삭제·해결 토글과 의미가 어긋나 스키마가 탁해진다. AI가 사람 작성자로 위장하는 것도 피한다.
- **왜 별도 탭으로 빼지 않는가**: 논의에 얹는 것이 이 기능의 요지다. 별도 탭으로 빼면 FR-14와 구별되지 않고, 논의를 읽은 의미가 사라진다.

## 10. 미결 사항

- ❓ **렌즈 정본의 관리 주체** — 렌즈 추가·개정을 누가 승인하는지 미정. RR 규칙 정본의 관리 주체 미결과 함께 정한다. → [08_DECISIONS_OPEN_ISSUES.md](개발문서/08_DECISIONS_OPEN_ISSUES.md)
- ❓ **의견 원문의 AI 입력 허용 범위** — 이 기능은 **사람이 작성한 의견 원문**을 LLM에 보낸다. FR-14는 목업과 기획안만 보냈다. 어떤 자료를 AI에 넣을 수 있는지 기준이 미확정이다. → [SECURITY_CHECKLIST 1절](docs/guidelines/SECURITY_CHECKLIST.md)
- ❓ **입력 총량 상한값** — 프로토타입은 임의값으로 두었다. 운영 LLM의 컨텍스트 한도 확정 후 재산정한다.
