# FR-09 Version v1.0

> **관련 문서**: [기능명세 인덱스](개발문서/기능명세/00_INDEX.md) | [PRD](개발문서/01_PRD.md) | [IA·화면](개발문서/03_IA_FUNCTION_SPEC.md) | [API/DB](개발문서/05_API_DB_SPEC.md)

## 1. 개요

결과물이 변경되면 불변에 가까운 Version 스냅샷을 만들고 작성 원인과 연결한다. (PRD 9절)
Version은 결과물의 논리적 스냅샷(상태)이고, 과정 기록은 History가 담당한다 — 두 모델은 분리된다(기획안 6-1절).

## 2. 동작 상세

- Version 번호(`version_no`)는 순차 부여되고, 각 Version은 `parent_version_id`로 이전 Version과 부모 관계를 가진다.
- 생성 원인을 `source_type`으로 남긴다: `AI_GENERATION / AI_REVISION / MANUAL_EDIT / IMPORT`. AI 작업이 원인이면 `source_job_id`로 Job과 연결한다 → [FR-05](개발문서/기능명세/FR-05_AI제작.md)
- 두 Version의 변경 전/후를 비교하고, 변경 사유와 연결된 의견·결정을 함께 볼 수 있다 → [FR-08](개발문서/기능명세/FR-08_반영결정.md)
- Version별 산출물 파일은 `version_files`로 연결하고 바이너리는 File Storage에 둔다.
- 사용자가 "왜 바뀌었는지"를 두 번 이상 클릭하지 않고 확인할 수 있어야 한다(03 UX 원칙).
- **(2026-09-05) 요소 단위 편집은 새 Version을 만들지 않는다.** 버튼 문구 하나를 고칠 때마다 Version이 늘면 계보가 잡음으로 가득 찬다. 대신 `element_patches`에 편집 이력으로 쌓고(누가·왜·언제·되돌림 여부), 결과물을 확정할 때 Version으로 승격한다.
  - Version = 합의된 스냅샷, 패치 = 그 사이의 손질. 이 구분이 [ARCHITECTURE.md](../../docs/architecture/ARCHITECTURE.md) 5절의 Version/History 분리와 같은 축이다.
  - 화면을 다시 만드는 것(재생성)은 기존 화면을 덮어쓰지 않고 **새 Version + 새 화면 행**을 만든다. 그래서 과거 Version의 패치와 의견은 그 Version 안에서 영구히 유효하다.
  - **(2026-09-08) 저장본은 덮어쓰지 않되, 서버가 읽을 때 얹는다(baking).** 화면에 보이는 것은 프레임이 패치를 얹은 결과지만 HTML 다운로드·AI 검토는 서버에서 저장본을 읽는다. 얹지 않으면 **그쪽만 편집 이전 상태를 본다** — 화면과 산출물이 갈린다. `lib/canvas/patches.ts`의 `bakeScreenHtml()`이 사본을 만들며 `screens.html_content`는 그대로 둔다. **서버에서 화면 HTML을 읽는 곳은 전부 이 함수를 거친다.**
  - ❓ **미결**: 패치를 Version으로 승격하는 시점을 사용자가 명시적으로 정하는지, 아니면 자동인지. 위 Version 승인 개념과 함께 정해야 한다.
- ❓ **미결**: Version 승인 개념 도입 여부 — [결정/미결](개발문서/08_DECISIONS_OPEN_ISSUES.md). 프로토타입은 버전 삭제를 허용하지만 정본은 "불변에 가까운" 스냅샷이 원칙 — 삭제 정책 확정 필요.
