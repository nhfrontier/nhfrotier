# FR-14 책임성 검토 v1.0

> **관련 문서**: [기능명세 인덱스](개발문서/기능명세/00_INDEX.md) | [PRD](개발문서/01_PRD.md) | [IA·화면](개발문서/03_IA_FUNCTION_SPEC.md) | [API/DB](개발문서/05_API_DB_SPEC.md) | **규칙 정본**: [RESPONSIBLE_DESIGN.md](docs/guidelines/RESPONSIBLE_DESIGN.md)

## 1. 개요

생성된 화면 설계·목업 산출물에서 **사회적·윤리적으로 문제가 될 만한 지점**을 AI가 찾아 의견으로 제시하고, 담당자가 반영 여부를 결정하는 기능이다.

네 축을 본다 — **표현·차별 / 금융소비자보호 / 다크패턴·설계 윤리 / 접근성·포용성**. 규칙 정본은 [docs/guidelines/RESPONSIBLE_DESIGN.md](docs/guidelines/RESPONSIBLE_DESIGN.md)이며, 이 문서는 그 규칙을 제품 기능으로 어떻게 운용하는지를 정의한다.

**왜 필요한가**: 이 제품은 AI가 만든 화면을 은행 업무 산출물로 쓴다. 성별 고정관념, 오인 유발 문구, 기본 체크된 동의, 판독 불가능한 색 대비가 섞여도 지금까지는 아무도 걸러내지 않았다. 저장소 전체에 이 축의 문서가 없었다.

## 2. 비범위 — 이 기능이 하지 않는 것

**[PRD 5절](개발문서/01_PRD.md)의 "자동 승인 또는 준법 판단의 완전 자동화" 비범위를 그대로 승계한다.** FR-14는 그 경계를 넓히지 않는다.

| 한다 | 하지 않는다 |
|---|---|
| "이 표현은 준법 검토가 필요해 보입니다" | "이 표현은 위법입니다" — 적법성 판정 |
| 목업에서 발견한 근거를 인용해 제시 | 근거 없는 지적 |
| 담당자에게 판단 재료 제공 | 담당자 대신 판단 |
| 준법 담당자에게 넘길 **경로** 제공 | 준법 검토 자체를 대체 |
| 의견으로 노출 | Export·공유 **차단** |

[08_DECISIONS_OPEN_ISSUES.md](개발문서/08_DECISIONS_OPEN_ISSUES.md) Q2("AI는 제안하고 최종 반영은 담당자가 결정한다")와 동일한 원칙이며, 기획안의 `우대금리 표현 → 추가 확인 → 준법 검토 요청` 선례를 따른다.

### FR-15와의 경계

[FR-15 UX 리스크 검토](개발문서/기능명세/FR-15_UX리스크검토.md)와 다크패턴(RR-C\*)·접근성(RR-D\*) 축이 겹쳐 보이지만 판정 단위가 다르다.

- **요소 하나로 답이 나오는 것은 FR-14다.** "선택 동의가 기본 체크되어 있는가"는 체크박스 하나만 보면 된다.
- **개수와 맥락이 문제인 것은 FR-15다.** "팝업이 흐름 전체에 네 개"는 요소를 아무리 들여다봐도 잡히지 않는다.

FR-14는 화면만 보고 자동 실행되며, FR-15는 의견까지 읽고 담당자 요청 시에만 실행된다.

## 3. 동작 상세

### 3-1. 1차 방지 — 생성 가드레일

목업 생성 프롬프트에 규칙 정본에서 파생한 설계 기본값을 덧붙여, 문제 요소가 애초에 덜 만들어지게 한다 → [FR-05](개발문서/기능명세/FR-05_AI제작.md)

**단, 프롬프트 지시는 통제가 아니다.** [SECURITY_CHECKLIST 4절](docs/guidelines/SECURITY_CHECKLIST.md)이 같은 논리를 이미 명시한다. 그래서 3-2의 2차 검토가 필수이며, 가드레일만으로 검토를 생략하지 않는다.

### 3-2. 2차 검토

**(2026-09-08) 검토 입력은 저장본이 아니라 요소 편집을 반영한 HTML이다.** 편집은 저장본을 덮어쓰지 않고 패치로 쌓이므로([FR-09](개발문서/기능명세/FR-09_버전관리.md) baking), 저장본을 넣으면 사람이 이미 고친 것을 AI가 다시 지적한다.

❗ **다만 이 검토는 여전히 첫 화면만 본다.** `mockup_versions.html_content`가 `sort_order` 0 화면으로만 채워지기 때문이다. `responsibility_findings`에 화면 구분 컬럼이 없어 다화면으로 넓히려면 스키마와 프롬프트를 함께 고쳐야 한다. ([FR-15](개발문서/기능명세/FR-15_UX리스크검토.md)는 전 화면을 본다) → ❓ 미결


- 목업 **생성 직후 자동 실행**된다. 담당자가 `다시 검토`로 수동 재실행할 수도 있다.
- 재실행은 이전 검토를 덮어쓰지 않는다. 새 검토 이력을 만들고 이전 결정은 그대로 보존한다.
- 결과는 규칙 목록에 비추어 **서버에서 검증한 뒤에만** 저장한다:
  - 정본에 없는 규칙 ID → 버린다
  - 근거(`evidence`)가 비어 있음 → 버린다
  - 카테고리는 모델 출력이 아니라 **규칙 정의**를 신뢰한다
- 지적할 것이 없으면 빈 결과를 그대로 보고한다. **억지로 채우지 않는다** — 노이즈가 섞이면 담당자가 전체를 신뢰하지 않게 되어 검토 자체가 무의미해진다.

### 3-3. 결정

담당자는 각 지적에 대해 넷 중 하나를 고른다. **반영 / 보류 / 반려**는 [FR-08](개발문서/기능명세/FR-08_반영결정.md)과 같은 체계이고, **준법 검토 요청**이 FR-14에서 추가된다.

| 결정 | 의미 |
|---|---|
| 반영 | 지적을 받아들여 고친다 |
| 보류 | 지금은 두고 나중에 판단한다 |
| 반려 | 지적이 타당하지 않다 |
| **준법 검토 요청** | AI도 담당자도 판단하지 않고 준법 담당자에게 넘긴다 |

- 금융소비자보호 축(RR-B\*)과 사전 체크 동의(RR-C01)는 `준법 검토 필요 = 예`로 표시되어 해당 버튼이 강조된다.
- 결정은 **누가·언제** 했는지와 함께 기록된다.
- **AI 제안과 사람의 결정은 UI에서 시각적으로 구분한다** — AI 카드는 축별 좌측 보더와 `AI` 표기, 사람 결정은 아바타 배지 ([03 UX 원칙](개발문서/03_IA_FUNCTION_SPEC.md)).

### 3-4. 운영 스택에서의 호출 경로

브라우저는 LLM을 직접 호출하지 않는다. 검토 호출은 AI Orchestrator 경유 서버 측 호출이며, 장시간 처리 시 비동기 Job 규칙을 따른다 → [FR-05](개발문서/기능명세/FR-05_AI제작.md) · [ARCHITECTURE 2·3절](docs/architecture/ARCHITECTURE.md)

## 8. 설계 판단 기록

- **왜 게이트가 아니라 자문인가**: 차단형은 [PRD 5절](개발문서/01_PRD.md) 비범위 및 [08 Q2](개발문서/08_DECISIONS_OPEN_ISSUES.md)와 충돌한다. AI 오판이 업무를 멈추게 하는 비용이 놓친 지적의 비용보다 크다고 판단했다.
- **왜 근거 인용을 강제하는가**: 근거 없는 지적은 담당자가 검증할 수 없어 결정을 내릴 수 없다. 서버에서 버린다.
- **왜 규칙을 문서와 코드 양쪽에 두는가**: 정본은 문서다. 코드 사본은 프롬프트를 규칙에서 **생성**하기 위한 것으로, 규칙을 추가하면 가드레일과 검토 지시가 함께 갱신되어 드리프트를 막는다.
- **왜 zod를 쓰지 않는가**: 구조화 출력에 `zodOutputFormat`을 쓰면 새 의존성이 필요하다. Anthropic SDK의 strict tool use가 같은 스키마 보장을 주므로 패키지를 추가하지 않았다 ([TECH_STACK D절 3항](docs/architecture/TECH_STACK.md)).

## 9. 미결 사항

- ❓ **준법 검토 요청의 수신자** — 준법 담당자 지정·알림·SLA가 정해지지 않았다. 현재는 결정 상태로만 남고 실제로 넘어가지 않는다. → [08_DECISIONS_OPEN_ISSUES.md](개발문서/08_DECISIONS_OPEN_ISSUES.md)
- ❓ **RR-B03 필수 고지 항목의 출처** — 카드·상품별 법정 표기 요소의 출처와 관리 주체가 미확정이다. 확정 전까지 규칙은 "자리가 있는가"만 본다.
- ❓ **규칙 정본의 관리 주체** — 규칙 추가·개정을 누가 승인하는지 미정.
