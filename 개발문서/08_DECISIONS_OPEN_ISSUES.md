| 참고 템플릿 선택 (FR-04) | **고르게 하지 않는다.** 고른 디자인 시스템의 **완성 화면을 전부** 화면 생성 프롬프트에 예시로 넣고, 지금 만들 화면에 어느 것이 가까운지는 모델이 판단한다. 사용자가 고르는 것은 디자인 시스템 하나뿐이다 (2026-09-08) |

| 디자인 시스템 자산의 성격 | `allone-bank`는 올원뱅크 앱에서 **UX 패턴만** 가져온 것이고 색·로고·서체는 **실제 CI가 아닌 대체재**다. ~~`nh-ibz`는 **컬러 토큰만 실제 NH**이며 로고·서체·아이콘은 대체재다.~~ → **(2026-09-08) `nh-ibz`의 로고와 CI 전용색상은 공식이다.** 심볼마크·워드마크를 공식 원본에서 벡터 추출하고(`scripts/trace-nh-ci.mjs`) PANTONE 규격 4색을 `--nh-ci-*` 토큰으로 신설했다. **서체·아이콘·일러스트는 여전히 대체재다.** 생성 결과 전체를 "NH 공식 디자인"이라고 부르지는 않는다 → [design-systems/README.md](design-systems/README.md) |

| 브랜드 시안 파이프라인 | 새 테이블·엔드포인트를 만들지 않고 FR-05의 AI Job을 `job_type = BRAND_CONCEPT`으로 재사용 |
| 시안 3안과 Version | 3안은 후보이며 Version이 아니다. 사용자가 하나를 **선택할 때** Version 1개가 생성된다 |
| 책임성 검토 (FR-14) | AI는 **준법 검토가 필요한 지점을 제시**할 뿐 적법성을 판정하지 않는다. Export·공유를 차단하는 게이트가 아니다 — PRD 5절 비범위를 넘지 않는다 |
| 책임성 검토의 근거 | 목업에서 그대로 인용한 근거가 없는 지적은 **서버에서 버린다.** 담당자가 검증할 수 없는 지적은 결정을 내릴 수 없기 때문 |
| 책임성 규칙 정본 | [docs/guidelines/RESPONSIBLE_DESIGN.md](docs/guidelines/RESPONSIBLE_DESIGN.md). 코드의 규칙 배열은 프롬프트를 규칙에서 생성하기 위한 사본이며, 정본이 아니다 |
| UX 리스크 검토 (FR-15) | FR-14와 **합치지 않고 별도 기능으로 둔다.** 입력(전 화면+의견 전문)·기준(질문 렌즈 vs 위반 규칙)·실행 시점(수동 vs 자동)이 달라 한 함수에 넣으면 두 결과가 다 흐려진다. 요소 하나로 판정되는 것은 FR-14, 개수·맥락이 문제인 것은 FR-15 |
| UX 리스크 검토의 트리거 | **담당자가 요청할 때만** 실행한다. 댓글마다 자동 실행하면 같은 지적이 반복되어 스레드를 오염시키고, 비용·지연이 예측 불가능해진다 |
| UX 리스크 검토의 근거 | 모델이 낸 인용 조각을 **기획안·화면 HTML·의견 원문과 글자 그대로 대조**하고, 살아남은 것이 없으면 그 지적을 통째로 버린다. 렌즈가 규칙보다 느슨한 만큼 근거는 FR-14보다 조인다 |
| UX 리스크 검토의 결과 위치 | 별도 탭이 아니라 **의견 목록에 사람 댓글과 시간순으로 섞어** 놓는다. 저장은 별도 테이블에 하며 `comments`에 AI 행을 넣지 않는다 |
| UX 검토 렌즈 정본 | [docs/guidelines/USABILITY_REVIEW.md](docs/guidelines/USABILITY_REVIEW.md). `mockup/lib/usability-lenses.ts`는 프롬프트 생성을 위한 사본이며 정본이 아니다 |
| 프로젝트 권한 모델 (FR-01) | **`OWNER` / `EDITOR` / `REVIEWER` / `VIEWER` 4단계로 확정** (2026-09-08). 기획안 7-3절 후보를 그대로 채택했다. 2단계(Owner/Member)로는 "읽기만 가능한 참여자"와 "의견은 내지만 반영 결정은 못 하는 검토자"를 표현할 수 없는데, FR-08 반영 결정과 FR-14·15 지적 결정이 이 구분을 전제로 한다. 권한 판정 지점은 Backend 한 곳(`@RequireProjectRole`)이며 프론트는 표시만 제어한다 |
| 권한 단계별 허용 범위 | `VIEWER` 읽기·다운로드 / `REVIEWER` + 의견·검토 요청 / `EDITOR` + 생성·편집·반영 결정·Export / `OWNER` + 프로젝트 설정·멤버 관리·삭제. 상위 단계는 하위 단계를 포함한다 |

## 3. 중요한 제품 의사결정
### Q1. 이 서비스는 디자인 시스템인가?
**아니다.** 디자인 시스템은 구성요소 중 하나이며, 제품의 중심은 업무 제작과 협의/의사결정 관리다.

### Q2. AI가 최종 판단하는가?
**아니다.** AI는 의견과 수정안을 제안하고, 최종 반영 여부는 담당자가 결정한다.

### Q3. 댓글/Version만 있으면 차별점이 되는가?
**아니다.** 핵심은 의견을 의사결정과 Version에 연결하고 이후 업무에서 재사용 가능한 자산으로 남기는 것이다.

### Q4. 카드·홍보물 시안을 만드는 것은 Q1(디자인 시스템이 아니다)의 번복인가?
**아니다.** FR-13은 새 디자인 체계를 세우지 않는다. 기존 NH 자산을 배치해 **방향 합의용 컨셉 시안**을 만들 뿐이고, 값은 시안 자체가 아니라 "어느 방향으로 갈지"가 Version·History에 기록되는 데 있다. 제품의 중심이 업무 제작과 의사결정 관리라는 Q1의 결론은 그대로다.

## 4. 향후 확장 방향
현재 프로젝트에서 축적되는 프로젝트/Template/Review/History 데이터는 이후 RAG와 유사업무 추천, 업무사례 검색, Agent 자동화의 입력 자산이 될 수 있다.
